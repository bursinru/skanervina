# «Своё Вино» — итоговое решение и техническое задание

**Версия:** MVP / конкурс «Лидеры цифровой трансформации 2026»  
**Формат первого релиза:** адаптивное web-приложение / PWA  
**Дальнейшее развитие:** приложения iOS и Android  
**Ключевая идея:** камера смартфона превращается в персонального AI-сомелье по российскому вину.

---

## 1. Краткое описание решения

«Своё Вино» — сервис распознавания вин по фотографии этикетки с последующей персональной рекомендацией.

Пользователь фотографирует бутылку или этикетку. Система:

1. находит этикетку на изображении;
2. выравнивает и очищает её;
3. распознаёт текст;
4. визуально сравнивает её с каталогом;
5. определяет конкретное вино;
6. показывает карточку вина, характеристики и оценку уверенности;
7. предлагает похожие позиции;
8. позволяет задать вопросы AI-сомелье;
9. если вина нет в каталоге «Своё Вино», пытается определить его и предлагает наиболее похожие российские альтернативы из нашего каталога.

Для конкурса система также предоставляет технический API, который принимает изображение и возвращает **Top-1 slug** распознанного вина.

Главная продуктовая формула:

> **Сканируй любую бутылку → узнай, что это → пойми, подойдёт ли она тебе → найди своё российское вино.**

---

## 2. Цели проекта

### 2.1. Главная конкурсная цель

Максимально точно определять конкретное вино из предоставленного каталога по фотографии и возвращать правильный `slug`.

Приоритет разработки для конкурсной версии:

**точность распознавания → стабильность → скорость → UX → дополнительные функции.**

Красивый интерфейс не должен ухудшать основную метрику распознавания.

### 2.2. Продуктовая цель

Создать не только технический сканер этикеток, а полноценный цифровой продукт для знакомства с российским вином:

- распознавание бутылки;
- объяснение вина простым языком;
- персональные рекомендации;
- сравнение нескольких вин;
- подбор к еде и ситуации;
- AI-сомелье;
- профиль вкусов пользователя;
- российские альтернативы зарубежным и отсутствующим в каталоге винам.

Предоставленный CSV содержит **4147 строк**, **2103 уникальных slug** и **2090 уникальных названий фотографий**.

Поля каталога:

- `Название вина`;
- `Категория`;
- `Цвет`;
- `Регион`;
- `Сорт винограда`;
- `Описание`;
- `Винодельня`;
- `Slug`;
- `Название фото`.

В поле `Сорт винограда` отсутствует значение только у **4 строк**.

В CSV много дублирующихся записей, поэтому перед построением индекса необходимо выполнить дедупликацию, прежде всего по `Slug`.

Из выгрузки Strapi необходимо автоматически выбрать только те изображения, которые связаны с винными карточками через поле `Название фото`. Медиафайлы сайта, статьи, блюда, фотографии людей, логотипы и другой контент в обучающий/поисковый индекс включать не нужно.

## 4. Контракт конкурсного API

Необходимо реализовать endpoint:

```http
POST /v1/eval/predict
Content-Type: multipart/form-data
```

Multipart-поле:

```text
image
```

Минимально допустимый ответ:

```json
{"slug": "kokur-suhoe-2025"}
```

Также можно поддержать внутренний расширенный формат API, но конкурсный endpoint должен всегда возвращать корректный Top-1 `slug`.

Внутренний endpoint продукта можно сделать отдельным:

```http
POST /v1/recognize
```

Пример расширенного ответа:

```json
{
  "status": "matched",
  "slug": "kokur-suhoe-2025",
  "confidence": 0.94,
  "wine": {
    "name": "Кокур сухое",
    "winery": "...",
    "region": "Крым",
    "color": "Белое",
    "grapes": ["Кокур Белый"]
  },
  "alternatives": [],
  "processing_ms": 780
}
```

# 5. Архитектура распознавания

## 5.1. Общая схема

```text
Фото пользователя
        ↓
Предобработка изображения
        ↓
Определение бутылки / этикетки
        ↓
Выравнивание перспективы
        ↓
 ┌───────────────────┬────────────────────┐
 ↓                   ↓                    ↓
OCR              Visual embedding     Local features
 ↓                   ↓                    ↓
Текстовые        Top-K похожих        Точное сравнение
кандидаты         этикеток             деталей
 └───────────────────┴────────────────────┘
                 ↓
              Reranking
                 ↓
              Top-1 slug
                 ↓
         confidence / карточка
```

Мы сознательно не строим решение как один огромный классификатор на несколько тысяч классов. Основной подход — **multimodal retrieval + reranking**.

Это проще расширять при появлении новых вин и лучше подходит для каталога, который постоянно меняется.

---

## 5.2. Этап A. Подготовка изображения

Перед распознаванием:

- исправить EXIF orientation;
- ограничить разрешение, например до 1600–2000 px по длинной стороне;
- нормализовать изображение;
- определить область бутылки/этикетки;
- убрать лишний фон;
- выполнить perspective correction;
- при необходимости повысить локальный контраст;
- подготовить несколько crop-вариантов.

Для MVP достаточно OpenCV + модель детекции/сегментации.

### Возможные технологии

- OpenCV;
- YOLOv8/YOLO11 segmentation;
- SAM/SAM2 — как эксперимент;
- лёгкая кастомная segmentation-модель после накопления разметки.

---

## 5.3. Этап B. OCR

OCR используется не как единственный способ распознавания, а как один из сигналов.

Из этикетки пытаемся получить:

- название;
- винодельню;
- сорт;
- год;
- регион;
- дополнительные слова.

Рекомендуемый стартовый вариант:

**PaddleOCR**.

Дополнительно можно протестировать:

- EasyOCR;
- Tesseract как baseline;
- отдельные OCR-модели для кириллицы и латиницы.

После OCR выполняем нормализацию:

- lower case;
- удаление шумовых символов;
- исправление типовых OCR-ошибок;
- транслитерация;
- fuzzy matching;
- поиск по названию и винодельне.

Пример:

```text
OCR:
"ПРИБОИ МАРЧЕНКО 2024"

Нормализация:
"прибой марченко 2024"

Кандидаты:
1. Прибой — Винодельня Марченко
2. Прибой Красное — Винодельня Марченко
3. Прибой Розе — Винодельня Марченко
```

---

## 5.4. Этап C. Визуальный поиск

Для каждого каталожного изображения заранее рассчитывается embedding.

Основной кандидат:

**SigLIP / SigLIP2**.

Baseline:

**CLIP / OpenCLIP**.

Для каждого wine slug храним:

```text
slug
catalog_image
image_embedding
metadata
```

В момент сканирования embedding пользовательского фото сравнивается со всеми embeddings каталога.

Так как каталог небольшой, поиск будет быстрым даже без сложной инфраструктуры. Для роста каталога используем:

**PostgreSQL + pgvector**.

Возвращаем, например, Top-20 визуальных кандидатов.

---

## 5.5. Этап D. Точное локальное сравнение

Главная проблема каталога — похожие бутылки одной линейки, где отличаются:

- цвет этикетки;
- мелкий текст;
- сорт;
- винтаж;
- небольшие элементы оформления.

Поэтому Top-K результатов SigLIP необходимо дополнительно сравнить по локальным визуальным признакам.

Кандидаты:

- SuperPoint + LightGlue;
- SIFT + RANSAC как простой baseline;
- LoFTR как эксперимент.

Пример:

```text
SigLIP:
Прибой белое       0.91
Прибой красное     0.89
Прибой розовое     0.87

OCR:
"СУХОЕ БЕЛОЕ"

LightGlue:
Белое: 132 корректных match
Красное: 41
Розовое: 34

Итог:
Прибой белое → Top-1
```

Именно этот этап может сильно повысить точность на визуально близких этикетках.

---

## 5.6. Этап E. Reranking

Финальное решение принимается не одним алгоритмом.

Пример формулы:

```text
final_score =
  visual_global_score * 0.45 +
  local_feature_score * 0.25 +
  ocr_name_score * 0.15 +
  winery_score * 0.08 +
  vintage_score * 0.04 +
  metadata_score * 0.03
```

Коэффициенты подбираются на validation set.

Важно: формула выше — стартовая гипотеза, а не фиксированное требование.

# 6. Как повысить точность и получить преимущество на конкурсе

## 6.1. Очистить каталог

Первое действие:

- дедупликация по slug;
- поиск отсутствующих картинок;
- поиск нескольких slug с одинаковой картинкой;
- удаление thumbnails, если существуют оригиналы;
- фильтрация мусорных медиа;
- проверка битых файлов;
- стандартизация форматов.

Создаём manifest:

```csv
slug,image_path,name,winery,region,color,grapes
```

---

## 6.2. Создать synthetic training / validation data

Одного каталожного изображения бутылки недостаточно для реального сканирования.

Из каждого изображения автоматически создаём варианты:

- perspective distortion;
- rotation;
- random crop;
- blur;
- motion blur;
- JPEG artifacts;
- shadows;
- low light;
- warm/cold lighting;
- glare;
- reflection;
- partial occlusion;
- шум камеры;
- бутылка на случайном фоне;
- масштабирование;
- имитация съёмки с полки магазина.

Не использовать слишком экстремальные трансформации, которых не бывает в реальности.

---

## 6.3. Собственный реальный validation set

Очень желательно вручную сфотографировать хотя бы несколько десятков/сотен бутылок:

- прямо;
- под углом;
- при плохом освещении;
- с бликом;
- далеко;
- крупно;
- частично закрытая этикетка;
- несколько бутылок в кадре.

Реальные фотографии важнее красивого synthetic dataset.

---

## 6.4. Hard negatives

Для каждой бутылки искать наиболее похожие неправильные варианты:

```text
Прибой белое
vs
Прибой красное
vs
Прибой розовое
```

И отдельно оптимизировать reranker именно на таких парах.

Это даст больший прирост, чем обучение на случайных разных бутылках.

---

## 6.5. Ensemble

На финальной версии можно сравнить несколько моделей:

- SigLIP;
- OpenCLIP;
- DINOv2;
- local features.

Если разные модели дают одинаковый Top-1 — confidence повышаем.

Если сильно расходятся — включаем дополнительный reranking.

# 7. Обработка вина, которого нет в каталоге

Это одна из ключевых продуктовых функций после конкурсного ядра.

Система сначала пытается определить `slug` каталога.

Если максимальный confidence ниже порога:

```text
confidence < threshold
```

пользователю не показываем ложное точное совпадение.

Вместо этого:

> **Похоже, этого вина пока нет в каталоге «Своё Вино».**

Далее система пытается определить:

- название;
- производителя;
- страну;
- регион;
- сорт;
- стиль;
- год.

На следующем этапе можно подключить внешний источник данных о мировых винах либо собственную расширенную базу.

После определения внешнего вина:

> **Мы нашли похожие российские вина.**

Пример:

```text
Ваше вино:
New Zealand Sauvignon Blanc

Стиль:
сухое, свежее, высокая кислотность,
цитрус, тропические фрукты

Российские альтернативы:
1. Wine A — 91% похожести
2. Wine B — 87%
3. Wine C — 82%
```

### Почему эта функция важна

Она превращает любой скан в точку входа в каталог российского вина.

Пользователь может фотографировать не только продукт «Своё Вино», а практически любую бутылку.

# 9. AI-сомелье

AI-сомелье — второй главный продуктовый модуль после сканирования.

Он не должен быть просто общим чат-ботом.

LLM получает контекст:

- найденное вино;
- каталог;
- характеристики;
- пользовательский Taste Profile;
- предыдущие оценки;
- избранное;
- бюджет;
- задача пользователя.

### Быстрые сценарии

- «С чем пить это вино?»
- «Подойдёт ли к стейку?»
- «Что взять к рыбе?»
- «Найди до 1500 ₽»
- «Хочу что-то менее кислое»
- «Что подарить?»
- «Найди похожее»
- «Найди российский аналог»
- «Что выбрать из этих трёх бутылок?»

### Принцип

LLM не придумывает товары.

Она получает разрешённый список wine_id / slug и объясняет выбор.

Схема:

```text
Запрос пользователя
        ↓
Фильтрация каталога
        ↓
Semantic / metadata retrieval
        ↓
Top-N реальных вин
        ↓
LLM
        ↓
Ответ + реальные карточки
```

# 10. Персонализация и Taste Profile

При первом использовании пользователь может пройти короткий onboarding:

1. Какие вина предпочитаете?
   - красные;
   - белые;
   - розовые;
   - игристые.

2. Сухое или сладкое?

3. Как относитесь к кислотности?

4. Лёгкое или насыщенное?

5. Какие сорта/вина уже нравятся?

После накопления действий профиль уточняется автоматически.

Используются:

- оценки;
- сканы;
- избранное;
- покупки/переходы;
- ответы «нравится / не нравится»;
- взаимодействия с рекомендациями.

У каждого вина можно показывать:

> **92% подходит вам**

И обязательно:

### Почему вам подходит

> Вы часто выбираете сухие белые вина.  
> Вам нравятся Sauvignon Blanc и яркая кислотность.  
> Вы высоко оценили несколько вин похожего профиля.

# 11. Рейтинги

Не смешивать разные типы рейтингов в одно число.

Можно показывать:

### Пользовательский рейтинг

```text
★ 4.5
324 оценки
```

### Экспертная оценка

```text
91 / 100
```

Только если есть достоверный источник.

### Персональная совместимость

```text
❤️ 92% для вас
```

Это прогноз алгоритма, а не общественный рейтинг.

# 12. Вкусовой профиль вина

Длинное описание из каталога необходимо дополнить быстрым визуальным слоем.

Пример:

```text
Лёгкое      ●──────○ Насыщенное
Мягкое      ───●───○ Танинное
Сухое       ●──────○ Сладкое
Мягкая      ────●──○ Высокая кислотность
```

Дескрипторы:

```text
🍐 Груша
🍑 Персик
🍋 Цитрус
🌼 Цветы
🍯 Мёд
```

На первом этапе такие признаки можно получать из существующих описаний посредством структурированного NLP/LLM enrichment и сохранять в базе, а не генерировать заново при каждом открытии карточки.

# 17. Главный экран

# 18. Визуальный эффект сканирования

Это одна из конкурсных «вау»-функций.

## Сценарий

1. Пользователь наводит камеру на бутылку.
2. Система определяет границы этикетки.
3. По краям появляется аккуратная светящаяся рамка.
4. Этикетка визуально отделяется от бутылки.
5. Perspective transform выравнивает её.
6. Она немного «выдвигается» вперёд как 3D-карточка.
7. По поверхности проходит scan line.
8. Одновременно запускается распознавание.
9. При успехе:

> ✓ **Вино найдено**

10. Этикетка плавно переходит в карточку вина.

### Технологии

- OpenCV;
- Canvas/WebGL;
- Three.js;
- CSS transforms;
- Framer Motion / GSAP.

Полноценный AR для MVP не нужен.

# 25. Confidence

Пользователь не должен получать выдуманную точность.

Не показывать `94%`, просто преобразовав cosine similarity в проценты.

Confidence необходимо откалибровать на validation set.

Внутренне:

```text
High confidence
Medium confidence
Low confidence
Unknown
```

UI:

### High

> **Мы нашли ваше вино**

### Medium

> **Похоже, это оно**

и 2–3 кандидата.

### Low / Unknown

> **Не удалось определить точно**

Предлагаем:

- переснять этикетку;
- выбрать из кандидатов;
- перейти к определению внешнего вина.

# 28. Производительность

Конкурсный скрипт отправляет запросы последовательно, поэтому необходимо минимизировать latency.

Цель MVP:

```text
p50 < 1.5 сек
p95 < 3 сек
```

При CPU-only сервере допускается более высокая задержка на раннем прототипе, но preprocessing и embeddings каталога должны быть рассчитаны заранее.

Нельзя пересчитывать embedding всего каталога на каждый запрос.

# 34. Почему решение может выиграть

## 1. Решает поставленную техническую задачу

Фокус на Top-1 идентификации конкретного `slug`, а не на декоративном AI.

## 2. Использует несколько независимых сигналов

Не только OCR и не только similarity:

- global vision;
- local visual features;
- OCR;
- metadata;
- reranking.

## 3. Работает со слабым исходным датасетом

Очистка, hard negatives, augmentation и собственный validation set.

## 4. Даёт сильный WOW на демо

- выделение этикетки;
- pseudo-3D;
- scan line;
- SVG-анимация бокала;
- плавный переход в карточку.

## 5. Имеет понятную бизнес-ценность

Неизвестное или зарубежное вино превращается в рекомендацию позиции российского каталога.

## 6. Имеет retention-механику

Сканирование → оценки → Taste Profile → персональные рекомендации → повторное использование.

## 7. Масштабируется после хакатона

PWA → iOS/Android без перестройки backend и ML-ядра.

# 35. Что НЕ делать в первой версии

Чтобы не потерять время:

- не обучать огромную LLM локально;
- не делать полноценный AR;
- не строить социальную сеть;
- не пытаться сразу собрать мировую базу всех вин;
- не делать сложный marketplace;
- не тратить основное время на 3D до появления стабильного распознавания;
- не использовать одну vision-модель без OCR/reranking;
- не выдавать similarity за настоящий confidence.

# 36. Критерии готовности конкурсной версии

Решение считается готовым, если:

- официальный тестовый скрипт проходит без ошибок;
- каждый запрос возвращает валидный slug;
- сервер не падает на последовательном прогоне;
- embeddings рассчитаны заранее;
- есть воспроизводимый pipeline;
- есть измеренный baseline;
- проведено сравнение нескольких подходов;
- выбран лучший вариант по Accuracy/Latency;
- камера работает на мобильном web;
- пользователь может получить результат без регистрации;
- UI корректно показывает High/Medium/Unknown;
- карточка вина открывается по slug;
- есть демонстрационный сценарий Unknown → российский аналог;
- есть работающий прототип сомелье либо хорошо подготовленный интерактивный demo flow.

# 38. Итог

Конкурсный продукт должен состоять из двух уровней.

## Уровень 1 — технологическое ядро

**Самое точное возможное распознавание конкретного вина из предоставленного каталога.**

Стек:

> **OpenCV + PaddleOCR + SigLIP + LightGlue + PostgreSQL/pgvector + FastAPI**

## Уровень 2 — продукт

**Красивый AI-сервис, который помогает человеку выбрать своё вино, а не просто узнаёт картинку.**

Ключевые функции:

> **Сканирование → распознавание → карточка → персональный Match → AI-сомелье → похожие вина → российский аналог → Taste Profile.**

Визуальный signature продукта:

> **Этикетка отделяется от бутылки и сканируется + SVG-бокал постепенно наполняется вином.**

Дальнейшая платформа:

> **Web/PWA → iOS + Android.**

Главный differentiator:

> **Сканировать можно не только позиции из каталога. Если это чужое/зарубежное вино, сервис понимает его и предлагает российский аналог.**

Это позволяет одновременно решить конкурсную CV-задачу, показать сильный технологический уровень и продемонстрировать продукт, который имеет смысл развивать после хакатона.
